# 「邮箱通了，却一封 CityU 来信都没到过」（v0.63.43，2026-09-16）

> 用户原话：**「为什么会出现这种问题，去解决。然后帮我做对每一个用户都可以一键刷新他们所有状态的按钮，
> 我要这个按钮可以选择全部人也可以单某个人」**。两件事，这一份写第一件（诊断 + 产品修法）；
> 第二件见 `docs/user-refresh-2026-09-16.md`。

## 1. 起因与调查

被检查的账号（下面叫「他」，真实地址不写进这里——这是要公开的文档）从**我们这一侧**看是一切正常的：

| 读数 | 值 |
|---|---|
| 注册 / 申请 | 07:43 UTC 注册，邀请码 07:42 发出（无错误） |
| 私人邮箱 | 一个 QQ 邮箱，12:57 配置，**授权码验证通过**，13:57 正常轮询，错误列为空 |
| 四盏灯 | 收信 **绿** · 模型/搜索 未测 · 出报告 红（没出过） |
| `setup_gap` | **空** —— 所以他**不在**「卡住的账号」名单里 |
| 库里 | 1 封邮件（`10000@qq.com` 的广告，因发件域不在允许名单被跳过） |

「已经配好了」和「真的收得到信」是两件事，而当时的产品只认前一件。于是做了一次**只读页眉扫描**
（`BODY.PEEK[HEADER.FIELDS …]`，不取正文、不动旗标、不移动游标，见 §5 的脚本形状）：

```
INBOX 一共 7 封（uid 485..494，2026-08-20 → 2026-09-16）
  From: email.nvidia.cn ×4 · email.developer.samsung.com ×1 · qq.com ×2
  7 封的 To / Delivered-To 全部只指向他的 QQ 地址
  FROM cityu.edu.hk = 0 · TO my.cityu.edu.hk = 0 · 其它文件夹（Junk/已删除/订阅）全空
=> 这 7 封里没有任何一封是「寄给学校地址、被转发过来」的
```

**结论：他缺的不是 App 里的任何设置，而是 CityU 那边的一条转发规则。**

两个必须写下来的坑：

1. **QQ 的 IMAP 把 `HEADER Delivered-To "<串>"` 当成匹配所有邮件**。同一批命令里
   `HEADER TO ...`、`FROM ...`、`SUBJECT ...` 都正常，只有 `HEADER Delivered-To` 和
   `HEADER X-Forwarded-For` 返回了「全部 7 封」，而逐封取页眉核对时那 7 封里**一封都没有**这两个头。
   如果只看搜索结果，结论会正好相反（「转发一直有效」）。**先怀疑工装**：用逐封真值去校服务器搜索。
2. **他自己的每日简报也在 INBOX 里**（uid 494，`【CityU 每日简报】2026-09-16 · 1 封邮件`）。
   它是产品自己发出去的（`GENERATED_PREFIXES` 因此在取信时被跳过），但它证明**这条链路的
   后半段是通的**：能读信、能生成、能经 QQ 的 SMTP 发回他自己的邮箱。

## 2. 为什么会「没人发现」

`Database.setup_gap()` 的定义是「还差私人邮箱」或「配了但从没连通成功」。转发规则**不在其中**，
因为它无法从我们这边验证——唯一的证据是**信真的到了**。于是出现了这一类账号：

```
注册 → 配好邮箱 → 授权码通了 → 学校那边的规则从没生效 → 永远收不到任何东西
                                                    ↑
                                     而他在每一张名单上都是「已完成」
```

这正是 v0.39/v0.61 那条教训的第三个面：**唯一看不见这个问题的人，就是这个问题的主人**。

## 3. 修法：把它变成第三种「卡住」

`setup_reminders.GAP_NO_MAIL = "no_mail"` —— 判据只有一条，且刻意不是「收件箱是空的」：

> **从未有过任何一封发件人在允许名单里的来信**（`count_analysed_messages == 0`）。
> 别人寄到他私人邮箱的广告不算，因为那证明不了学校的规则存在。

* **门槛 24 小时**，量的是**邮箱配置至今**（`mailboxes.updated_at`）而不是注册多久：
  昨天注册、五分钟前才接通邮箱的人不欠我们一个解释。
  常量放 `Database.NO_SCHOOL_MAIL_HOURS`，**设置向导、首页 `next_step`、提醒邮件三处共用一份**。
  （首页原先自己写了一个两小时的冷启动判断，同一个事实两种说法、两个门槛——已删。）
* **自动那一档受门槛限制**；运营者**点名**（`audience="selected"`）不受限制——那是决定，不是启发式。
* **换了一句话就不算「已经提醒过」**：印章里记着发的是哪一组（`时间|组`），
  上次告诉他「你还没配好」、这次该告诉他「转发没生效」，旧印章不该盖住新的问题（`needs_notice`）。
  没有组信息的旧印章按「已经告诉过他」处理——猜他收到的是哪一封，就是给人寄第二封的办法。
* **信里写的是学校那一边的步骤**（`{steps}` 在这一组渲染 CityU 官方 FAQ 的路径 + 那条循环警告），
  不是私人邮箱的授权码教程——那一步他已经做完了。正文里明写**判断依据**是发件人地址，
  并给出第二种可能（学校这段时间确实没发信），让收到信的人能反驳我们。

## 4. 用户自己看到什么

"四步走"的第 3 格「CityU 转发已生效」以前只有一句「还没有收到过任何 CityU 邮件」，
而且**只写在 tooltip 里**（手机上根本没有 hover）。现在：

* 第 2 步下面（`#forward-check`）**画出结论**，`todo` 语气 = 「还没到，去做第 2 步」；
  超过 24 小时则变成 `warn`：「邮箱接通已经 X 天，但一封 CityU 来信都没到过。回第 2 步检查……」
  （并写清只统计发件人是 CityU 地址的邮件）。
* 首页 `next_step` 那一张警告卡与它是**同一句话**（`Database.forwarding_step`），测试钉住两者相等。

「自动不打扰、但运营者现在就能手点」这两半都按设计生效了。

### 5.1 验收当场抓到的第三件事：绿灯 ≠ 那条链通过

同一轮验收里看见他的四盏灯是 **收信 ✓ · 模型 ✗ · 搜索 ✗ · 出报告 ✓**——而他一封信都没收到过。
查下去：他唯一发出过的报告是 **14:00 的每日简报**（`reports.kind='daily'`）。

每日简报由**确定性清单**生成，**零封来信时也发得出去**：它证明「收信通 + 发信通」，
但**证明不了「有来信被读懂并回答了」**——而 `Database.verification_lights` 的注释一直写着那盏灯
「cannot be green unless the mailbox was read, the model answered and the mail went out」。
**这句话对简报不成立。**

（补一句现场核对：这台机器上「每日简报的综览」是**开着**的，所以那份简报确实调过一次模型
——`token_usage` 里有一行 `kind='digest'`、137/20 tokens。所以准确的措辞不是「简报不碰模型」，
而是「简报不证明来信被处理过」；综览关掉时它连模型都不碰，那又是另一种更弱的情形。）
v0.63.44 起那盏灯分开说：

* 有过真正来自来信的报告 → 「报告真的发出去了」；
* 只有过每日简报 → 「只发出过每日简报：收信和发信是通的，还没有任何一封来信被分析过」。

**没有把灯改红**：东西确实发出去了，红灯会冤枉它。改的是**它说的话**——
这一格存在的全部意义就是让运营者一眼看出「这个账号到底通没通」。

## 6. 这件事不该被做成什么样

* **不要**把「出报告」那盏灯做成可以测出来的（见 `docs/user-refresh-2026-09-16.md`）。
* **不要**用「收件箱里有没有邮件」当转发证据：私人邮箱本来就一直在收别的信。
* **不要**为了让数字好看去读用户正文——判断这一档只需要**发件人地址**与**是否处理过**。
* **不要**给他加已读回执或追踪像素来确认「信到没到」：能观测的只有「服务器接受了这封信」。
