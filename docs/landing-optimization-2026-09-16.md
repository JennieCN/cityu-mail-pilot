## 一、批注在说的其实是三件事

8 张图、12 条批注，去掉重复以后只有三个母题：

| 母题 | 出现在 | 一句话 |
|---|---|---|
| **① 删掉多余的解释** | 批注 1、2、3、7、12 | 读者不需要知道「这句话我顺过标点」「这钱谁出的」「怎么找到下面那节」。解释性文字每多一句，真正的那句话就淡一分。 |
| **② 把「装到手机上」提到最显眼处** | 批注 6、9 | 访客变用户的那一步是**装到手机上**，不是「它是怎么工作的」。现在这句话躺在 `#how` 的**最后一行**、还是灰最小的字。 |
| **③ 把行话换成普通话** | 批注 4、5、8、10、11 | `BODY.PEEK[]`、`IMAP`、「授权码与 API key 加密保存」——这些是**写给我自己看的**，不是写给大二学生看的。 |

一句话总结这份方案：**首页要少解释、早给出路、说人话。**

## 二、逐条对照

### 1. 署名只留名字

**位置**：首屏故事末尾。

```diff
- <p class="sig">余剑篪（原话引用，只顺了标点）</p>
+ <p class="sig">余剑篪</p>
```

批注原话是「只留『余剑篪』」。「只顺了标点」这种自我说明是**写给考据者的**，读者只需要知道这段话是谁说的。注意第 194–198 行的故事正文**一字不动**——批注针对的是署名，不是正文。

### 2. 首屏那句只留「内测期间免费」

**位置**：首屏按钮下面那行小字（`#pilot-count`）。

```diff
- {{PILOT_COUNT}}内测期间免费，给结论的那部分由管理员出钱。
+ {{PILOT_COUNT}}内测期间免费。
```

**后半句不是删掉这个事实**，而是它在这个位置**说不完**：读者此刻不知道「给结论的那部分」指什么（那是模型调用），也不知道「管理员」是谁。这个事实在下文有两处**说得更准**的地方，都保留：

- `#how` 第二节：「内测期间默认用管理员提供的模型 key，你不花钱，想换成自己的 key 也可以……」
- `#privacy` 的披露框：「内测期间默认用管理员的 API key，所以这些调用记录会落在管理员的模型账号里……」

**被钉着**：`test_bulletin.test_the_page_still_tells_the_truth_about_the_pilot_size` 要求页面里有「内测期间免费」四个字（保住）；`test_compliance.test_every_page_agrees_about_who_pays_and_that_a_key_is_still_allowed` 要求 `/` 上同时出现「管理员」与「自己的」（上文两处仍在，保住）。

### 3. 布告栏的说明整句删掉

**位置**：`web.py::render_bulletin` 生成的那段小字。

```diff
- <p class="note">运营者写给所有人的通知。没登录也看得到，所以这里不会有只跟某个账号有关的内容。</p>
```

「布告栏」三个字加下面的公告标题已经说明了一切；而且这段解释**默认根本渲染不出来**（没有公告时整节都不出现），属于写了个没人看的说明。删掉后标题直接接公告，视觉上更紧。

### 4. 留言板说明改成可提取的要点

**位置**：`#guestbook` 开头那段（现为一句口语长句）。

```diff
- <p>没注册也能写。写下的话<b>先只有我看到</b>，我读过之后决定要不要匿名放到这一页上——
- 所以这里不会有广告，也不会出现任何人的邮箱。</p>
+ <p class="note">不用注册也能留言。提交后先只有运营者看到；是否刊登、以什么昵称刊登，由运营者决定。</p>
+ <ul class="plain">
+   <li>刊登时一律匿名，不会出现任何人的邮箱</li>
+   <li>最多 2 个链接，留言一直保存到你或运营者删掉为止</li>
+ </ul>
```

原句的问题不是口语，而是**三件事挤在一个破折号里**（谁能写 / 谁先看到 / 为什么墙上干净），读者提取不出要点。改成一句陈述 + 两条清单，每条只讲一件事。

### 5. 截图下面那行改成名词短语

**位置**：`#how` 上面那张真实界面截图的 `<figcaption>`。

```diff
- <figcaption>这是它每天发给你的东西。上面是真实的运行界面，不是效果图。</figcaption>
+ <figcaption>软件每日推送消息真实运行界面（非效果图）</figcaption>
```

「这是它每天发给你的东西」和上面的正文重复；「不是效果图」这个**重要**的信息被埋在一个否定句里。改成图注体（名词短语 + 括号补充），一眼扫过去就知道这是真机截图。

### 6. 「装成一个应用、课间看一眼就够」加粗并提到最显眼处 ★

**这条是整份方案里唯一动版式的改动，也是最值钱的一条。**

原位置：`#how` 最后一行（灰小字，`p.note`），在首屏往下滚两屏的地方。

```diff
- <p class="note">手机上可以装成一个应用，打开就是同一个清单，课间看一眼就够，不用开电脑。
- 安卓和 iPhone 的装法在<a href="#download">下面那节</a>里一步一步写了。</p>
```

改为放在**首屏**（`h1` + standfirst 之下、三个按钮之上），并加粗、带指路链接：

```diff
+ <!-- 访客变用户的那一步是「装到手机上」，所以这句不放 #how 的末尾，
+      放首屏、加粗，并且自己就是通往安装那一节的入口。 -->
+ <p class="pitch"><b>手机上可以装成一个应用，打开就是同一个清单，课间看一眼就够。</b>
+ <a href="#download">看怎么装 →</a></p>
```

`.pitch` 用现有的 `--ok-ink` / `--ok-bg`（主题里已声明的 token），左侧一条 3px 竖线，与隐私那节的披露框同一套视觉语言——**不新增颜色**。

### 7. 删掉「装法在下面那节」这句指路

**位置**：`#how` 末尾（与第 6 条同一段）。

整句删除。理由：首屏已经有一个通往安装那一节的粗体入口，页内 `#download` 也已在顶部导航里；**在解释「它怎么工作」的地方插一句「怎么安装看下面」，是把两件事混在一起**。删掉后 `#how` 干净收在「费用和调用记录都在你自己的服务商账号下」。

### 8. 开源那一节保留形状、缩小字号

**位置**：`#source`（服务端注入）。

```diff
- #source li{margin:6px 0;color:#46443e}
+ /* 只有认真的读者会读这一节，所以它保留结构但整体降一档字号：
+    存在感靠边框和底色，不靠字号跟正文抢。 */
+ #source{font-size:14.5px}
+ #source li{margin:5px 0;color:#46443e;font-size:14.5px}
```

形状（圆角卡片 + 十个链接 + 许可证）不动——**这是 AGPL 第 13 条要求的可见入口**，缩的是字号不是内容。

### 9. 「装到手机上」这一节的层级与步骤 ★

三处改动：

**(a) 标题加一个「先装它」的眉标**，让这一节在滚动中被认出来：

```diff
  <section id="download">
+ <p class="kicker">先装它 · 全部安装方式都在这一节</p>
  <h2>装到手机上</h2>
```

**(b) 两个安卓方法的小标题说清「区别是什么」**，而不是「方法一 / 方法二」：

```diff
- <h3>安卓 · 方法一：下载安装包</h3>
+ <h3>安卓 · 方法一：下载安装包 <span class="tag">功能最全</span></h3>
...
- <h3>安卓 · 方法二：不下载安装包</h3>
- <p class="note">如果不想看到「未知来源」的提示，用这条更省事。</p>
+ <h3>安卓 · 方法二：用浏览器直接装 <span class="tag">最省事</span></h3>
+ <p class="note">不下载任何文件，也看不到「未知来源」的提示。</p>
```

**(c) 四步安装的每一步加一个粗体动词开头**，让「第几步做什么」不需要读完整句：

```diff
- <li>用手机上的浏览器打开这一页，点上面的下载按钮。文件会存进「下载」文件夹。</li>
+ <li><b>下载</b>：用手机上的浏览器打开这一页，点上面的下载按钮。文件会存进「下载」文件夹。</li>
- <li>点开刚下载的文件。系统会先拦一下，说不能安装未知来源的应用——
-     点「设置」，找到<b>你刚才用的那个浏览器</b>，打开它的「允许安装未知应用」，然后返回再点一次。</li>
+ <li><b>允许安装</b>：点开刚下载的文件。系统会先拦一下，说不能安装未知来源的应用——
+     点「设置」，找到<b>你刚才用的那个浏览器</b>，打开它的「允许安装未知应用」，然后返回再点一次。</li>
- <li>装的时候可能还会提示「Play 保护机制」或「未经检测的应用」。
-     这个安装包没有上架 Google Play，所以这类提示是正常的，选「仍然安装」就行。</li>
+ <li><b>仍然安装</b>：装的时候可能还会提示「Play 保护机制」或「未经检测的应用」。
+     这个安装包没有上架 Google Play，所以这类提示是正常的，选「仍然安装」就行。</li>
- <li>装好后桌面上会出现图标。以后有新版本，回到这一页重新下载、直接覆盖安装即可，
-     账号和数据都不会丢。</li>
+ <li><b>以后更新</b>：装好后桌面上会出现图标。以后有新版本，回到这一页重新下载、直接覆盖安装即可，
+     账号和数据都不会丢。</li>
```

**不改成图标/emoji**：项目到目前为止一个字都没有用过表情符号，`ol.steps` 的编号本身就是步骤标记（`::marker` 已经加粗着色）。加图标要么引入外部图片（违反邮件那条「零外部图片」的同源洁癖，也会让 CSP 之外的资源多一个来源），要么引入图标字体——**收益是审美，成本是依赖**，所以用「粗体动词 + 原有编号」实现同一个目的。

**被钉着**：`tools/landing_check.js` 要求这一节里仍有「允许安装未知应用」「添加到主屏幕」「必须用 Safari」「看不到浏览器的地址栏」四句（一句不少）。

### 10. 隐私清单说人话 ★

**位置**：`#privacy` 的 `ul.plain`。

| 原文 | 改后 | 为什么 |
|---|---|---|
| 只读收信（IMAP `BODY.PEEK[]`），不标记已读、不移动、不删除 | **只读收信，不标记已读、不移动、不删除** | `BODY.PEEK[]` 是 IMAP 协议里的取信命令，**是写给我自己看的**。要证明「只读」的从来不是这个词，而是后面那三个「不」 |
| 只处理本校发件域的来信，其余只记一行「已跳过」和发件人 | 只处理本校邮箱发来的邮件，其余只记一行「已跳过」和发件人 | 「发件域」是行话 |
| 报告发出后，数据库里的邮件正文立即清空 | 报告发出后，我们这边不留邮件正文 | 「数据库」对读者无意义；「我们这边」才是他关心的 |
| 授权码与 API key 加密保存，改密码会吊销全部会话 | 邮箱授权码和 API key 加密保存；改密码后，其它设备上的登录会立刻失效 | 「吊销全部会话」是行业词；「其它设备上的登录会立刻失效」才是用户能验证的事 |
| 不向你或任何第三方上报使用情况，没有任何遥测 | 不统计你的使用行为，也没有任何遥测 | 同义，更短 |
| 不用你的邮件训练模型，不卖、不共享给广告方 | 不用你的邮件训练模型，不卖也不共享给广告方 | 标点 |

**被钉着**：`tools/landing_check.js` 要求正文仍有「只读」和「没有任何遥测」（两条都保住）；`test_compliance` 不读这一节，但它读的披露框一字不动。

### 11. 申请内测那一节讲清「名额是什么」★

**位置**：`#apply` 开头。

```diff
- <p>留一个邮箱，我们人工看过之后把邀请码发给你。用你打算收摘要的那个私人邮箱，
- 这样也顺便验证了它能收信。</p>
+ <p>这个工具要有一台一直开着的服务器替你读信、写信，所以<b>光下载、装到手机上还用不了</b>——
+ 内测采取邀请制，我在这台服务器上给你开一个名额，你收到邀请码才算拿到。</p>
+ <p>留一个邮箱，我人工看过之后把邀请码发给你。</p>
```

原句只说「会发生什么」，没说**为什么需要这一步**——一个刚看完「下载安装包」的访客会合理地以为下载完就能用。补上因果之后，申请就不再像一道多余的门。

**第 12 条**（批注要求「留一个邮箱……也顺便验证了它能收信」只留前半句）已包含在上面的 diff 里：「这样也顺便验证了它能收信」删除——**「验证收信」在授权码接通那一步才真的发生**，在申请环节说它是提前承诺。

## 三、实施时补的两处（批注没写、但同一类问题）

1. **`#how` 里的 `AES-256-GCM`**（原文：「授权码用 AES-256-GCM 加密后按用户隔离存放」）——
   和第 10 条同一种毛病：**算法名对访客没有任何可验证的含义**，而《隐私政策》里写得比这精确
   （「使用 AES-256-GCM 信封加密，并按用户与用途隔离」）。改成「授权码加密保存，每个账号的密文
   互相隔离」，并在句末指向隐私政策。**技术细节搬家，不是删掉。**
2. **留言板那一节的称呼统一**——说明句改成「运营者」之后，同一节里的标签还写着
   「只给**我**看」「留了**我**才能回你」、空板那行还写着「先给**我**看」。一节里两种人称
   是改动留下的半成品，所以这三处跟着统一成「运营者」。**故事那一节的第一人称不动**——
   那是作者在讲自己的事，不是客服口吻。

## 六、为什么第 15 条没有用 emoji

批注举的例子是 🖐（安卓上「点这里」的手势）。最后用的是 **CSS 画的编号圆点**，原因有三条，
都不是审美偏好：

1. **同一个字形在不同系统上不是同一个东西**：🖐 在 iOS、Android、Windows 上是三套画风，
   而这一页的排版全是中文衬线 + 系统无衬线，插一个彩色手势会像别人家的图。
2. **emoji 会被输入法/系统替换或吃掉**：某些安卓机型的字体回退会把个别码位渲染成方框，
   而这一步恰好是**路人变用户**的那一步，不能赌设备。
3. **它要表达的信息是「第几步」，不是「点」**：编号圆点直接给出序号，还和 `<ol>` 的语义
   一致（读屏软件读的是列表序号）；🖐 表达的是「点」，反而没有进度感。

一句话：**要的是「步骤标识」，不是「一个手势图」**。如果运营者要的就是 emoji，改一行 CSS 即可
（`ol.steps li::before{content:"🖐"}`），但那会把项目「零 emoji」的记录打破，所以留给他决定。

## 附：2026-09-20 的板块顺序调整（v0.64.1，采纳 PR #3 的方向）

有人提了 PR（`Bear-qaq`，#3「调整内测页板块顺序并精简首页介绍」），方向是对的：

迎面就是一块公告和一张留言表单，而「它是怎么工作的」被推到很后面。

但它那版有三处我们没照做，理由都留在这里：

| 删掉第一屏那句「这是个把 CityU 邮件读一遍…的小工具」，先讲作者的故事 | **不动** | 标题本身是一句自白（「我漏看过很多封邮件」），删掉那句平实的说明，陌生人要读完三段故事才知道这页是干什么的——这正是 2026-09-16 那 8 张批注要解决的问题。故事仍然紧跟在后面，一点没少 |
