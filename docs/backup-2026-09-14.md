# 备份：轮转、异地、以及"什么才是真正的风险"（v0.40.0，2026-09-14）

## 先纠正一条欠账

清单里写着「没有轮转策略（会一直涨）」。**这是错的**——`backup.py` 一直保留最新 7 份。
但同时暴露了一个比"没有轮转"更糟的真相，看生产目录：

```
pilot-20260914T125311Z.sqlite3   ← 12:53  部署前备份
pilot-20260914T140123Z.sqlite3   ← 14:01  部署前备份
pilot-20260914T141246Z.sqlite3   ← 14:12  部署前备份
...（共 7 份，全是那个下午的部署备份）
```

**当天 03:20 的日报备份已经不在了。** 因为 `deploy_pilot.sh` 的升级前备份
**调用的是同一个函数、写进同一个目录**，于是「最新 7 份」这个策略在一次部署七个版本的日子里，
把整条日报链挤没了。**按数量保留，分不清"一周的日报"和"一下午的部署"。**

### 改法：按时间保留

| 规则 | 默认 | 为什么 |
|---|---|---|
| `INFE_PILOT_BACKUP_KEEP_DAYS` | **7 天**（2026-09-18 从 14 改） | 时间窗口，而不是数量——这才是"保留多久"的正确单位。改成 7 是因为备份不可压缩、份数是磁盘的最大乘数，40 GB 盘上把 100 人的可用期从 26 个月拉到 46 个月（见下） |
| `INFE_PILOT_BACKUP_KEEP_MIN` | 7 份 | 下限。停机一个月的机器回来跑一次备份，不能把仅有的几份按"太旧"删掉 |
| `INFE_PILOT_BACKUP_KEEP_MAX` | 60 份 | 上限。100 MB 的库不能靠 7 天悄悄把磁盘写满 |

### 2026-09-18 补充：这套规则实际会留下几份，以及占多少磁盘

按天数保留修好了「一下午的部署挤掉日报」，但**没有修掉「部署和日报抢同一个窗口」** ——
每次升级仍然写一份到同一目录，只是现在它以「天」为单位占位。所以份数不是窗口天数，
要用规则算。`tools/backup_retention_model.py` 用 `prune()` 的同一套判断按真实日历天模拟：

| 场景 | 稳定份数 |
|---|---|
| 只有每日 03:20 的 timer | **8 份**（今天 + 往前 7 天） |
| 每天还部署一次 | **15 份** |

**备份占用不是常数**，它是「份数 × 当时的库大小」，库随时间线性增长，所以它跟着涨。
`tools/disk_budget.py` 按 40 GB 盘（留 15% 余量 = 34 GiB 可用）、100 人每天 3 封算：

| 时点 | 总占用 | 其中备份 |
|---|---|---|
| 1 年 | 12.3 GiB | 11.4 GiB |
| 2 年 | 20.1 GiB | 18.3 GiB |
| 3 年 | 27.9 GiB | 25.2 GiB |
| 4 年 | 35.7 GiB | 32.2 GiB |

**写满 34 GiB：第 46 个月**（对照：14 天是 26 个月，3 天是 52 个月）。

**别指望压缩**：备份里的负载是 AES-GCM 密文，实测 gzip 后 **95%（1.0×）**。
本地目录里本来就是未压缩的 `.sqlite3`，压缩只用在异地那份。

完整分析与实测见 `docs/sqlite-performance-2026-09-18.md` §6。

## 三条风险，按严重程度排

| # | 风险 | 现状 | 这一轮做了什么 |
|---|---|---|---|
| 1 | **主密钥只在那台机器上** | `INFE_PILOT_MASTER_KEY` 在 `pilot.env`，**刻意不进任何备份**。没有它，备份里的邮箱授权码与 API key 全部解不开——备份全在也没用 | `--check` 会**明说这句话**并把它算作"需要处理"。没有替运营者保存它（那需要新的凭据保管决定），但不再让"有备份"暗示"能恢复" |
| 2 | **数据库和它的备份在同一块盘上** | 机器/磁盘没了就全没了 | 新增**可选**的 WebDAV 异地推送；不配就还是"只在本机"，但 `--check` 会说这是个单点 |
| 3 | **备份停了没人知道** | systemd 的 `OnFailure=` 只在**跑了但失败**时触发。定时器被停用、机器一直没开机、维护后忘了重新 enable——**都不会触发** | 哨兵新增 `backup_missing` / `backup_stale`（36 小时，即"少跑了一次"）与异地 `offsite_failed` / `offsite_stale` |

## 异地推送：为什么是 WebDAV

调研过（`litestream` 的 cron 指南、restic/borg/rclone 社区做法）后选了最小的一条路：

- **不引新依赖、不装守护进程。** restic / borg / rclone / litestream 都能做这件事，但每一个都是
  要长期维护的外部二进制——本项目的铁律是"运行时只有 `cryptography` 一个依赖"，
  **一个只在一台 2 GB 机器上每天跑一次的备份，不值得换来一个需要跟着升级的组件。**
  WebDAV 就是**一次带 Basic 认证的 HTTP PUT**，标准库二十行。
- **远端命名用"几号"滚动**（Litestream 的 cron 指南里的做法）：`pilot-<DD>.sqlite3.gz`
  加 `pilot-latest.sqlite3.gz`，远端自然只留约一个月，**不需要远端列目录、也不需要远端删除**。
  这点很关键：WebDAV 的 `DELETE` / `PROPFIND` 恰恰是各家实现差异最大、最可能被关掉的两个操作，
  一个"因为清理失败而失败"的备份任务就是自找的故障。
- **推送失败不算本地失败**：本地那份是升级路径依赖的东西，先本地、后异地；
  异地失败记进 `offsite-state.json`，由哨兵告诉你。

配置（三个变量进 `pilot.env`，**绝不要写在命令行**）：

```bash
INFE_PILOT_BACKUP_WEBDAV_URL=https://dav.example.com/remote.php/dav/files/me/cityu-pilot
INFE_PILOT_BACKUP_WEBDAV_USER=me@example.com
INFE_PILOT_BACKUP_WEBDAV_PASSWORD=应用专用密码
```

**URL 里内嵌 `user:password@` 也认**：好几家服务商发的就是这种 URL，而 `urllib` 会直接拒绝它
（`InvalidURL: nonnumeric port`）。所以在读取配置时就把凭据拆出来放进请求头——
**常见写法能用，密码也照样进不了日志**（打印出来的 URL 一律经过 `safe_url()` 去掉 userinfo 与 query）。

## 怎么配（一条命令）

```bash
sudo bash /opt/cityu-mail-pilot/pilot_app/set_backup_target.sh
```

它会依次问地址、用户名、应用密码（**密码用 `read -s`，不回显、不进历史、不进任何对话记录**），
写进 `pilot.env` 后**立刻用每天那份 systemd unit 真跑一次备份**——同样的用户、同样的
`EnvironmentFile`、同样的 `ProtectSystem=strict` 与出网限制。手跑
`python -m pilot_app.backup` 证明不了"那个 unit 在沙箱里能不能连出去"。

参数：`--url/--user` 可预填、`--remove` 清除（回到只在本机）、`--no-verify` 只写配置。
失败时会打印 WebDAV 的报错原文与**退回原文件的命令**；本地备份永远不受异地失败影响。

Koofr 的具体值：地址 `https://app.koofr.net/dav/Koofr`，用户名是登录邮箱，
密码是**设置页生成的应用密码**（不是登录密码）。

## 免费额度够不够

Koofr 免费 10 GB。这份库 580 KiB，gzip 后约 150 KiB，远端按「几号」滚动命名，
一个月最多 31 份 ≈ **5 MB**。

## 现在怎么看现状

```bash
sudo systemd-run --uid=cityumail --property=EnvironmentFile=/etc/cityu-mail-pilot/pilot.env \
  --working-directory=/opt/cityu-mail-pilot --pipe --wait --collect \
  /opt/cityu-mail-pilot/.venv/bin/python -m pilot_app.backup --check
```

输出本地最新一份有多旧、保留策略、异地配没配/最后一次成功或失败、以及主密钥那句提醒；
有问题时**非零退出**，可以接告警。

## 测试

`pilot_app/tests/test_backup.py`，**24 条**：

- 保留：窗口内保留、超期删除、**"一下午的部署不能挤掉日报链"（就是上面那个真实事故）**、
  下限保护、上限封顶；
- 异地：**起一个真的 HTTP 服务器收 PUT**（不是 mock——签名与编码正是会错的地方）、
  收到的字节解压后与数据库逐字节相同、凭据进 Authorization 头、507 与不可达都**报告而不抛出**、
  URL 里的密码不出现在任何输出里、dry-run 不碰服务器、状态文件读写；
- 哨兵：没有备份 / 备份过期是 critical 且解释 `OnFailure=` 的盲区、推送失败与推送停摆、
  **没配异地不算故障**、重复周期是 24 小时、**备份目录不可读时既不报警也不崩**。

写这批测试时抓到两个真问题：`push_offsite` 会把 `http.client.InvalidURL` 抛出去
（文档说"never raises"），以及哨兵在 `/var/backups` 不可读的机器上**整个挂掉**——
后者是 macOS 上跑测试时发现的：`is_dir()` 在父目录不可搜索时**抛异常而不是返回 False**。
**哨兵挂掉的代价是所有检查一起停，比少查一项严重得多。**

## 真机验证（2026-09-14 完成）

Koofr 免费 10 GB，目标 `https://app.koofr.net/dav/Koofr`。用 `set_backup_target.sh` 配好，
**它启动的是每天那份 systemd unit**，所以验的是"unit 在 `ProtectSystem=strict` 下能不能连出去"，
不是手跑模块。结果：

| 检查 | 结果 |
|---|---|
| 推送 | `offsite-state.json` → `ok: true`，182 KB，两个滚动文件名 |
| `backup --check` | 结论行：「本地有新鲜备份、异地有推送、主密钥在你手上」，退出码 0 |
| 保留策略生效的样子 | 目录从 7 份涨到 11 份（都在 14 天窗口内，**一份都没删**）——当时的窗口是 14 天，2026-09-18 起改为 7 天 |

**失败演练也做了**，而且做得很干净：用假地址跑一次（**不带 `EnvironmentFile`**，
所以真正那份配置一个字都没动；带的话 `--setenv` 会被 EnvironmentFile 覆盖，第一次就吃了这个亏）：

```
offsite FAILED: URLError: <urlopen error [Errno 111] Connection refused>
backup created: pilot-20260914T162636Z.sqlite3      ← 本地那份照样成功
```

状态文件记下 `ok: false` 与错误原文，**哨兵随即报 `offsite_failed`（warning）并带上错误文本**；
再正常跑一次，状态回到 `ok: true`，哨兵**对备份这件事完全沉默**。

> **2026-09-15 更正**：这里原本写着「哨兵也回到只剩 `backup_stale: 备份正常`（info）」。
> 那条「备份正常」其实是个**每小时响一次的假警报**——`_should_send` 的设计是「详情变了就重发」，
> 而它的详情里带着按小时取整的备份年龄，于是每过一小时就重发一封。
> **健康的检查应该是沉默的**（另外十一条都是这样），所以那条 finding 已删除；
> 备份从「过期」回到「新鲜」仍会走正常的 `recovered` 路径收到一次「已恢复」。
> 要确认备份现状用 `python -m pilot_app.manage backup --check`。

**结论：异地这条路是通的，失败也是看得见的。**

## 还缺什么（说清楚，别让"有备份"暗示更多）
1. **只有运营者能确认远端真的躺着那两个文件**（我拿不到 Koofr 的凭据）。
   `ok: true` 的含义是"服务器接受了这次 PUT"（HTTP 201），不等于"文件可下载"。
   打开 Koofr 网页应能看到 `pilot-latest.sqlite3.gz` 与 `pilot-<日>.sqlite3.gz`。
2. **主密钥的离线副本仍然靠人**。`--check` 只能提醒。真要机械化，需要你决定把它放哪
   （密码管理器 / 打印机 / 另一台机器），那是新的凭据保管决定。
3. **异地只有一份滚动副本**（约一个月）。真正的恶意删除/勒索防护需要"不可变"或追加式存储，
   那是另一个量级的方案。
