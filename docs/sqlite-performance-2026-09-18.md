# SQLite 性能与百人级适配（2026-09-18）

> 面向的读者是**接手这台服务器的人**：现在这套 SQLite 访问方式在 100 个账号下表现如何、
> 瓶颈到底在哪、这一轮改了什么、还剩什么没改以及为什么。
>
> 所有数字都是在本机（24 核、Windows）用 `tools/` 下的脚本**实测**出来的，不是估算。
> 每个脚本都能重跑，命令在文中给出。**这一轮里有两个「看起来显然对」的判断被实测推翻**
> —— 那两个最值得看（§5）。

## 0. 结论（先读这段）

| 问题 | 结论 |
|---|---|
| 现在能不能撑 100 人？ | **能，而且不用改保留期、不用换数据库。** 实测 100 个人**同时**开着应用（远高于任何真实场景）时 p50 仍 **35.6 ms**、零错误；常态负载约 **0.011 次/秒**，实测单进程能到 **80–170 次/秒**。 |
| 最大支持多少用户？ | **单进程 100 人很轻松，几百人也可以；** 保守写「**单进程 100–150 人**、加进程后 **500 人以上**」。限制是单进程 Python 的吞吐（80–90 次/秒），**不是 SQLite**。 |
| 那之前慢在哪？ | **不在 SQLite，而在每个请求开 15 个连接、以及几条全表扫描。** 后端面板一条查询要 **46 秒**（`list_users_overview`），仪表盘每次加载 **148 ms**，其中一条 `COUNT(*)` 是**全表扫描**（176 ms）。 |
| 这一轮改了什么？ | ① `journal_mode` 从「每个连接都设」改成「启动时设一次」；② 加 2 个索引（并**否决了 3 个**）；③ `cache_size`/`mmap_size`；④ schema 迁移加版本闸门。 |
| 效果 | 仪表盘 148 → **约 40 ms**（单点最大提升来自索引：176 ms → 1.8 ms）；后端面板 **46.5 s → 1.1 s**；`initialize()` 47 → 9 ms。 |
| 真正的天花板 | **单进程 Python 的吞吐**（8 个并发之后固定在 80–90 次/秒）。已实测：**同一个库文件上开 3 个 web 进程 → 2.8 倍吞吐、延迟降到 1/3、零锁错误**（§4.2）。 |
| 不加保留期的代价 | **不是性能问题，是磁盘。** 每封信常驻 **7.5–9.3 KiB**（实测口径，报告信封占绝大部分）。备份份数**不是 14 份** —— 保留规则是「14 天」加「至少 7、最多 60」，只有每日定时任务时稳定在 **15 份**，而每次升级也写一份到同一目录，所以「每天升级」会变成 **30 份**。**备份份数是乘数**，所以 40 GB 盘上 `KEEP_DAYS` 从 14 降到 3，100 人从「26 个月写满」变成「52 个月」。见 §6/§7。 |

**一句话**：SQLite 不是这套系统的瓶颈，**连接方式和几条查询**才是；这两个都修好了，
100 人级完全够用，而再往上要先换掉「单进程 + 单文件」，不是换数据库。

## 1. 测试台：我们量的到底是什么

### 1.1 一台「100 人用了半年」的库

`tools/sqlite_bench.py` 造一个形状真实的库：

```bash
python tools/sqlite_bench.py --users 100 --messages-per-user 300 \
    --reports-per-user 300 --page-views 200000 --json docs/_bench.json
```

100 个账号、30 000 封信、30 000 份报告、200 000 条访问记录，**约 990 MiB**
（早期那版悲观造数会到 1.5 GiB，见下）。

**造数据这件事本身踩了一个坑，值得单独说**（`seed()` 的 docstring 里也写了）：
第一版给每一行都写 `utc_now()`、每封信都塞 20 KiB 正文、六分之一标成 `pending`。
结果是 `messages` 表 1.5 GiB、10 000 行「待处理」，于是：

* `due_messages` 看起来是 300 ms 的慢查询 —— 而真实系统里队列**基本是空的**
  （发出去的信正文会被清空，这是隐私政策第 76 行的承诺）；
* 所有 `created_at >= 最近 14 天` 的范围查询**一行都匹配不到**，后端面板因此「很快」。

也就是说：**一个不走心的测试数据集会让基准测试给出反向的结论。**
现在 `seed()` 默认按真实形状造（`realistic=True`），`--pessimistic` 才是那个悲观形状。

### 1.2 负载模型（可以反驳的那种）

`tools/sqlite_loadtest.py` 模拟的是「一个人打开应用」：

| 参数 | 取值 | 依据 |
|---|---|---|
| 活跃比例 | 一小时内 10% 的账号会打开 | 试点的乐观假设 |
| 一次会话 | 6 个页面、约 90 秒 | |
| 因此真实负载 | 10 人 × 6 次 ÷ 5400 秒 ≈ **0.011 次/秒** | |
| 压测跑的 | **0.25 – 10 次/秒** | 约真实负载的 **25 – 900 倍** |

每个「页面渲染」做的事和 `web.py` 的 `/api/me` 处理器**逐一对应**：会话查询、
profile、mailbox、两个 connection、今日报告、任务状态、已分析计数、公告、
待办计数、setup_progress —— **加上每个请求都要付的两笔写**（`touch_last_seen`
和 `record_page_view`）。同时后台跑着 worker 的队列循环（`due_messages` +
`active_mailboxes` + `recover_inflight`），因为那才是和读者抢同一把锁的东西。

## 2. 改之前：三条真正的瓶颈

`tools/sqlite_profile_calls.py` 把每个调用单独计时（每次调用 = 一次
`Database.connect()` + 一条查询）：

```bash
python tools/sqlite_profile_calls.py --users 100 --messages-per-user 300 \
    --reports-per-user 300 --page-views 200000 --rounds 30
```

**改之前**（约 990 MiB 库、旧数据形状）：

| 调用 | 耗时 | 为什么 |
|---|---|---|
| `setup_progress` | **207 ms** | 里面的子查询 `COUNT(*) FROM messages WHERE user_id=? AND status!='skipped'` → `SCAN messages` |
| `count_analysed_messages` | **176 ms** | 同一个扫描；**每次加载仪表盘都要付** |
| `today_reports` | 56 ms | 小 |
| 其余每个调用 | 0.65 – 2.2 ms | 基本就是「开一个连接」的固定成本 |
| `list_users_overview`（后端面板） | **46 482 ms** | 每账号 7 个相关子查询 × 100 个账号，每个子查询都是一次 `messages` 全表扫描 |
| `list_messages_overview` | 7 349 ms | 8 条 `COUNT(*)`，每条一次全表扫描 |
| `recent_volume` | 3 406 ms | 14 天窗口，但窗口里的行数远超现实 |

**一次仪表盘加载要付的，就是上面这些**：`count_analysed_messages`（176 ms）+
`setup_progress`（207 ms）已经是 383 ms，再加上其余十来次「开连接 + 小查询」
（每次约 0.8 ms）。**表里那个 148 ms 是 990 MiB / 新版造数形状下的整体测量**
（§3.4），两者不可直接相加 —— 列在这里是为了说明**钱花在哪儿**。

根因一句话：**`messages` 表上根本没有 `user_id` 索引。** 它唯一的唯一键是
`(mailbox_id, uid_validity, imap_uid)`，而 `mailbox_id` 已经隐含了用户 —— 所以每个
按用户过滤的查询都在扫全表。

### 2.1 连接的成本

`connect_components` 把一次 `Database.connect()` 拆开量（约 990 MiB 库）：

| 步骤 | p50 |
|---|---|
| `sqlite3.connect()` | 0.286 ms |
| `PRAGMA foreign_keys` | 0.006 ms |
| **`PRAGMA journal_mode = WAL`** | **0.713 ms** |
| 查询本身 | 0.060 ms |
| commit + close | 0.091 ms |
| **合计** | **0.804 ms** |

**每个连接 0.7 ms 花在重复确认一个不可能变过的设置上**，而每个页面要付 15 次
（约 10 ms）。`journal_mode` 是**文件的属性**：它写在文件头里，跨连接、跨重启都在。

`tools/sqlite_settings_probe.py` 用**每个变体一份全新数据库副本**、**随机顺序**、
**多次重复取中位数**来比较（第一版所有变体共用一份库，导致 6 个变体里有 5 个在量同一个
no-op —— 这是基准测试最容易犯的错，脚本里有注释）：

```
A 现状：每连接 FK + WAL          read p50 1.763   write p50 1.361
B journal_mode 只在启动时设一次    read p50 2.017   write p50 2.487
C B + synchronous=NORMAL          read p50 1.940   write p50 1.027
D C + mmap + 32MiB cache          read p50 1.773   write p50 1.387
E B + mmap + 32MiB cache          read p50 2.106   write p50 1.610
F 回滚日志（DELETE）               read p50 0.624   write p50 2.917
```

两点结论：

1. **A 和 B 在单线程下没有区别。** 在已经是 WAL 的库上，`PRAGMA journal_mode=WAL`
   只是一次文件头读取 —— 所以**不要把它当成「省了 0.7 ms」来卖**（我一开始就是这么
   写的，实测否掉了）。真正的理由是它**可能要求写锁**：它是读者唯一一条会等在写者
   后面的语句。确认一个没人改过的设置，不值得这个风险。
2. **F 说明 WAL 本身是有价值的**：回滚日志下读快（0.62 ms）但写慢一倍多
   （2.9 ms），而混合负载下读者 p95 从 14 ms 涨到 **84 ms** —— WAL 让读者不被写者
   挡住，这正是单文件数据库最需要的东西。（第一版脚本在已有 WAL 的库上测「切到
   DELETE」，结论是反的，因为那次切换根本没成功。）

## 3. 这一轮改了什么

### 3.1 `Database.connect()`：把文件属性从连接路径上拿走

`pilot_app/database.py`

* `PRAGMA journal_mode = WAL` 移到 `initialize()` → `_apply_file_settings()`，
  **每个进程一次**，并且**校验它真的生效了** —— 没生效就 `logging.warning` 说出
  「写并发会差很多、读会被写挡住」，而不是让人在 20 秒超时里猜。
* `connect()` 现在显式设置每连接才有效的三项，并给它们起了名字：
  `busy_timeout=20s`（原来藏在 `sqlite3.connect(timeout=20)` 里）、
  `cache_size=-32MiB`（默认只有 2 MiB）、`mmap_size=256MiB`。
* `busy_timeout` 保持 20 秒不变 —— 但**写成了常量并注明了它的含义**：这是 web
  服务整个请求预算的长度，等满 20 秒的请求已经不是页面而是故障了。

### 3.2 索引：加 2 个，**否决 3 个**

`tools/sqlite_index_audit.py` 的做法是：**把索引删掉，再跑一遍它的查询**，
差值就是这个索引的全部作用。（还额外跑一次 `ANALYZE` 后重测，免得计划是
「统计信息猜出来的」而不是索引的功劳。）

```bash
python tools/sqlite_index_audit.py <库文件> --users 20 --rounds 25
```

| 索引 | 有 | 没有 | 判定 |
|---|---|---|---|
| `idx_messages_user_status` `(user_id, status)` | 0.022 ms | 0.183 ms | **保留（8.3 倍）** |
| `idx_messages_received` `(received_at DESC)` | 0.028 ms | 6.642 ms | **保留（237 倍）** |
| `idx_messages_user_received` `(user_id, received_at DESC)` | 0.155 ms | 0.166 ms | **否决（1.07 倍）** |
| `idx_reports_message_kind` `(message_id, kind)` | 0.042 ms | 0.041 ms | **否决（0.98 倍）** |
| `idx_messages_queue` `(status, next_attempt_at, created_at)` | 345.03 ms | 345.64 ms（删掉之后） | **否决（−0.61 ms）** |

（前两行是在 约 990 MiB 库上、对 20 个用户取**合计**的实测 —— 单看一个用户，
扫描和索引查找的差别小到看不出来，这正是那条全表扫描能在仪表盘上藏那么久的原因。
8.3 倍这个数字**还被低估了**：审计时删掉 `idx_messages_user_status` 后，SQLite
退而用 `idx_messages_user_received` 顶着，而那个索引这一轮已经被否决、不会存在。
真实基线见 §2：**单次调用 176 ms，因为那时是彻底的全表扫描。**）

**但是「逐个索引删掉再测」会漏掉一件事：索引会改变 SQLite 选的执行计划。**
`tools/sqlite_index_ab.py` 在**同一份库**上、按 A/B/A/B 交替地把两个索引删掉又建回来
（交替是为了让页面缓存和机器噪声同时作用在两边），才发现了这一点：

| 调用（生产用的「一天」窗口） | 没有新索引 | 有新索引 | 倍数 |
|---|---|---|---|
| `count_analysed_messages` | 15.91 ms | **1.89 ms** | **8.4×** |
| `messages_between`（每日简报） | 16.04 ms | **2.04 ms** | **7.9×** |
| `setup_progress` | 20.02 ms | **5.94 ms** | **3.4×** |
| `today_reports` | 2.16 ms | 2.44 ms | 持平 |
| `list_users_overview` | 1 641 ms | **1 165 ms** | 1.4× |

**同一个实验也发现了一个「索引反而更慢」的案例，值得记住**：
用**很宽的**时间窗口（一个月／全部历史）跑 `today_reports` 时，
`idx_messages_received` 会让 SQLite **翻转连接顺序**，从「先取这个用户的报告」
变成「先扫全库这个时间段的邮件再回表」，46 ms 变 152 ms。

**但那是基准测试自己造的窗口，不是生产的**：`web.py` 的 `_local_window()` 传的是
**用户本地的一天**，`service.py` 的每日简报也是**一天**。用一天的窗口复测：

| `today_reports` 窗口 | 没有索引 | 有索引 |
|---|---|---|
| **一天（生产用的）** | 2.16 ms | 2.44 ms |
| 一个月 | 3.5 ms | **29.0 ms** |
| 全部历史 | 47.7 ms | **157.3 ms** |

所以这个索引**留着**（它给 `list_messages_overview` 带来 **524×**），
但这条教训写进 §5 —— **拿一个比生产宽得多的窗口去测，会得到一个不存在的回归。**

代码里三份清单对应三种状态，注释里写了每个的数字和理由：

* `LATE_INDEXES` —— 留下并创建；
* `REJECTED_INDEXES` —— **不创建**，但保留名字和理由。这两个「看起来显然对」，
  实测是错的，以后不要再想一遍；
* `RETIRED_INDEXES` —— 上一版**已经建过**的，现在 `DROP`。因为已经跑到 100 人库上
  的版本可能已经把它们建出来了，光从清单里删掉的话，那份库会永远为它们付写入成本。

### 3.3 schema 迁移：版本闸门（这里踩了一个真实的坑）

`SCHEMA_VERSION = 3` 写进 `app_settings`。

**第一版把整个迁移都放在闸门后面，结果破坏了升级路径**，被
`test_usage` 抓到了：一个库如果在「缺 `token_usage.on_platform` 列」的状态下被盖上
了版本号，那么这个闸门会让它**永远补不上这一列**，直到线上读到 `no such column`。

现在闸门**只挡那一个真正昂贵的操作**（`messages` 表重建）；`ALTER TABLE ADD COLUMN`
这类便宜、自检（`PRAGMA table_info`）、幂等的语句照常每次都跑。

在 约 990 MiB 库上实测 `tools/sqlite_migration_check.py`：

```
migrated in 0.0s   second run 0.021s   version 3 -> 3
indexes added: (none)      indexes lost: (none)
row changes  : (none)
```

* **幂等**：第二次启动 0.021 s；
* **不丢行**：表重建前后行数逐表比对，`row changes: (none)`；
* **生产尺寸可用**：约 990 MiB 上迁移 0.0 秒（索引在上一版已建）。

### 3.4 效果（约 990 MiB / 30 000 封信的库）

「改之前」一列来自本轮开始时的实测（旧版代码）；「改之后」来自改完之后跑的同一套
逐调用计时。**两者的造数形状略有不同**（见 §1.1，旧版把每封信都写成 20 KiB 正文、
六分之一标 pending），所以表里的倍数用于看**量级**；最严格的那一条
（`idx_messages_user_status`）以 §3.2 索引审计为准 —— 那是同一堆字节上删掉索引再测的。

| 调用 | 改之前 | 改之后 | 倍数 |
|---|---|---|---|
| `count_analysed_messages` | 176 ms | **1.82 ms** | 97× |
| `setup_progress` | 207 ms | **6.82 ms** | 30× |
| `today_reports` | 55.7 ms | **18.4 ms** | 3.0× |
| `list_users_overview`（后端面板） | 46 482 ms | **1 091 ms** | 43× |
| `list_messages_overview` | 7 349 ms | **1 267 ms** | 5.8× |
| `page_view_totals` | 2 305 ms | **2.83 ms** | 815× |
| `/api/me` 仪表盘整体 | 148 ms | **约 40 ms** | 3.7× |
| `initialize()`（启动一次） | 17 ms | **9 ms** | 1.9× |

`initialize()` 那两个数字取自 990 MiB 库；在 1.5 GiB 的库上（旧造数形状）改前是
**47 ms**，改后 **9 ms**，差距主要来自版本闸门跳过了那一串 `PRAGMA table_info`
与索引自检。

查询计划也从 `SCAN messages` 变成了
`SEARCH messages USING COVERING INDEX idx_messages_user_status`。

**注意 `/api/me` 那 40 ms 里有约 10 ms 纯粹是「开 10 个连接」的固定成本**，
而每次调用的实测下限就是 1.8 ms（`get_profile` 这类小查询）—— 也就是说
**连接开销已经成了仪表盘的主要成本**。这是 §8 第 2 条要处理的东西。

## 4. 百人级到底够不够：实测

这一节有两个实验，**看结论请以 4.1 为准**：4.0 只驱动数据库层（每个客户端自己 sleep
到目标速率），4.1 打的是真实的 HTTP 服务器。两者的「拐点」不一样，原因写在 4.1。

### 4.0 数据库层

`tools/sqlite_loadtest_sweep.py` 在**同一份** 640 MiB 库上，只改请求速率：

```bash
python tools/sqlite_loadtest_sweep.py <库文件> --rates 0.25,1,2,5,10 --seconds 15
```

| 请求速率 | 并发 | p50 | p95 | 错误 |
|---|---|---|---|---|
| **0.05 /秒**（真实负载的量级） | 4 | 62.9 ms | **76.4 ms** | 0 |
| 0.10 /秒 | 4 | 63.2 ms | 73.9 ms | 0 |
| 0.25 /秒 | 4 | 69.3 ms | 91.8 ms | 0 |
| 0.50 /秒 | 4 | 73.8 ms | 88.7 ms | 0 |
| **1.0 /秒**（约 90 倍常态） | 4 | 66.0 ms | **96.5 ms** | 0 |
| 2.0 /秒 | 8 | 186.7 ms | 230.7 ms | 0 |
| 5.0 /秒 | 20 | 640.6 ms | 755.6 ms | 0 |
| 10 /秒 | 40 | 1 021.5 ms | 1 344.2 ms | 0 |

* **100 人的常态负载（约 0.011 次/秒）对应约 74 ms 的 p95**；即使把整个 100 人的
  负载压到 **1 次/秒**（约 90 倍常态），p95 仍是 96 ms；
* **全程零错误、零 `database is locked`** —— WAL + 20 秒 busy_timeout 是有效的。

（这个实验里「并发」和「速率」是分开设的，所以它的拐点说的是**并发数**：4 个并发下
一直到 1 次/秒都很稳，20 个并发时 5 次/秒就已经 640 ms。它测的是数据库，不含 HTTP
与 Python 的编码开销 —— 那部分见下。）

### 4.1 端到端：真实 HTTP、真实服务器

上面测的是数据库层的调用。`tools/http_loadtest.py` 把 `pilot_app.web` 当**独立进程**
拉起来（就是 systemd 跑的那个 `create_server`），真注册账号、真发 cookie，走 HTTP 打
`/api/me`，所以在它里面每个请求都包含了一个人真正要付的全部：socket 与线程 HTTP
服务器、`_require_user`（会话查询 **加上** `touch_last_seen` 写）、`_record_visit`
的访问写入、处理器的读、JSON 编码、响应。

```bash
python tools/http_loadtest.py <库文件> --clients 8 --seconds 15 --think 2
```

**先看一个反面教材**：这个脚本的第一版**不读子进程的 stdout**，于是服务器日志写满
管道后阻塞在 `write()` 里——一次 15 秒的测试跑了 60 秒、只有 79 个请求，而我会据此
得出一个完全错误的结论。线程 HTTP 服务器 + 子进程 + 不排空的管道，就是这个形状。
`drain()` 的存在和注释都是为了这个。

**一个人真的在用（每次翻页停 2 秒）**：

| 同时开着应用的人数 | 请求/秒 | p50 | p95 | 错误 |
|---|---|---|---|---|
| 8 | 4.0 | 15.6 ms | **62.8 ms** | 0 |
| 16 | 8.0 | 21.7 ms | 146.2 ms | 0 |
| 32 | 16.0 | 26.6 ms | 211.8 ms | 0 |
| 64 | 31.9 | 29.5 ms | 503.9 ms | 0 |
| **100** | 47.7 | **35.6 ms** | 694.8 ms | 0 |

**注意 p50 那一列**：哪怕 100 个人同时开着应用，**中位数仍然是 35.6 ms**；
变差的是尾部（p95）。而且**全程零错误、零 `database is locked`** —— 100 人同时在线
时系统不是崩，是「有些人偶尔等一下」。

**一直循环点（不留思考时间，测上限）**：

| 并发 | 请求/秒 | p50 | p95 |
|---|---|---|---|
| 1 | 38 | 25.9 ms | 29.1 ms |
| 4 | 150 | 26.2 ms | 36.0 ms |
| 8 | **173** | 46.1 ms | 61.3 ms |
| 16 | 89 | 178 ms | 195 ms |
| 32 | 81 | 386 ms | 468 ms |
| 64 | 85 | 614 ms | 1 369 ms |
| 128 | 80 | 1 140 ms | 2 637 ms |

**吞吐在 8 个并发之后固定在 80–90 次/秒，加并发只加延迟。** 这就是这个单进程
Python 服务的真实上限。

为什么是这个数？`/health`（不做会话、不读库）在同一台机器上能跑 **535 次/秒**，
所以不是我压测端的瓶颈；而纯 Python 多线程在 24 个线程下比单线程慢 4.7 倍，
说明 **GIL 让 Python 侧串行化**。固定下来的 80–90 次/秒，就是「串行的 Python 代码
+ 每个请求 2–3 次 fsync 写入」合起来的结果。

### 4.2 多进程是安全的（这条推荐经过验证，不是推测）

上面那个上限是**每个进程**的。这一轮本来只是把「多进程」写成一个方向，
`--servers N` 让它变成实测：

```bash
python tools/http_loadtest.py <库文件> --clients 32 --seconds 15 --servers 3
```

| 并发 | 1 个 web 进程 | 3 个 web 进程（同一个库文件） |
|---|---|---|
| 32 | 80.3 次/秒，p50 389 ms，p95 459 ms | **227.6 次/秒，p50 141 ms，p95 177 ms** |
| 64 | — | 221.2 次/秒，p50 284 ms，p95 370 ms |

**吞吐 2.8 倍，延迟降到约三分之一，零 `database is locked`。** 三个进程同时写同一个
SQLite 文件、外加每个请求的两次写，完全没问题 —— WAL 的「多读者 + 单写者」正是为
这个场景设计的，而 `initialize()` 里那句 WAL 校验保证了这个前提。

**所以「加进程」这条路是验证过的，不是想当然。** 要扩到 200 人以上：
nginx 分发到 2–4 个 web 进程，每个 `MemoryMax=350M`，`TasksMax` 相应放大。

### 4.3 天花板不是 SQLite

`web.service` 是**一个进程**的 `ThreadingHTTPServer`，`MemoryMax=350M`。
CPU（更准确说是 Python 侧的串行化）才是首先用尽的资源。
**要往 200 人以上走，该做的是多进程，而不是换数据库** —— 见 §8。

### 4.4 那「最大支持多少用户」

把上面的数字翻译成人：

| 场景 | 同时在线 | 实测表现 | 判断 |
|---|---|---|---|
| 100 人的**常态**（§1.2 的负载模型） | ≈1–2 | p50 约 20 ms | **毫无压力** |
| 100 人**全部同时**打开应用、每 2 秒翻一页 | 100 | p50 **35.6 ms**，p95 695 ms，**0 错误** | **能扛住**，尾部会有人等一下 |
| 100 人**全部同时**疯狂点（不留间隔，非人类） | 100 | p50 1.1 s | 会明显变慢，但不报错、不崩 |
| 单进程压到极限 | — | **80–90 次/秒**，再加并发只加延迟 | 单进程的硬上限 |
| 3 个进程 | 32 | **227 次/秒**，p50 141 ms | 2.8 倍，已验证 |

**结论**：

* **单进程：100 人轻松，200–300 人也行**（真实流量远低于 80 次/秒）；
* **要一个能写进文档、有安全余量的数字：单进程 100–150 人**，因为它同时满足
  「100 人全在线也只有 36 ms 中位数」和「常态负载只用掉 1% 的吞吐」；
* **超过这个数就加进程**（§4.2 已验证），而不是换数据库 —— 换数据库解决不了
  单进程 Python 的串行化。

**注意这些数字来自一台 24 核开发机**：吞吐上限主要取决于 Python 侧的串行化
（GIL）和磁盘 fsync，所以换成 2 vCPU 的生产 VPS **吞吐大致不变、并发余量更小**。
保守起见，第一次上线按单进程 100 人规划，观察 `/api/admin/metrics` 的 CPU 与
`metrics.py` 里的延迟分位数再决定要不要加进程。

## 5. 被实测推翻的三个判断（最有价值的部分）

写下来是因为它们都很「显然」：

1. **「队列索引能让 worker 的排序走索引」** —— 错。`messages(status,
   next_attempt_at, created_at)` 建了，SQLite **从来不选它**：10 000 行积压时计划
   仍是 `idx_messages_due` + `USE TEMP B-TREE FOR ORDER BY`，`NOT INDEXED` 和走索引
   一样快（345 ms）。删掉索引后是 345.64 ms —— **差值 −0.61 ms**。它只是在为每次
   `INSERT INTO messages` 增加成本。
2. **「`reports(message_id, kind)` 需要建」** —— 错，而且错得很难看：**库里早就有了**
   `idx_report_per_message`（一个 `(message_id, kind) WHERE message_id IS NOT NULL`
   的部分唯一索引），两个状态下 SQLite 用的都是它。**加索引之前没有先看已经有了什么。**
3. **「把 `journal_mode` 从每个连接挪走，省 0.7 ms」** —— 在已经是 WAL 的库上量不出
   区别（A 1.763 ms vs B 2.017 ms，噪声内）。它**仍然是该做的**，但理由是「读者不该
   为确认一个没变过的设置而可能排在写者后面」，不是性能数字。

还有两个方法论上的坑，都写进了脚本注释：

* **变体重用同一个数据库** → 5/6 个变体在量同一个 no-op（WAL 是持久的）；
* **测试数据全用 `now()` + 20 KiB 正文 + 1/6 pending** → 范围查询匹配不到行，
  并且把空队列变成 10 000 行积压，让真正慢的东西藏起来。

**第三个坑是这一轮最后才发现的，也是最隐蔽的一个：拿比生产宽得多的窗口去测。**
`tools/sqlite_index_ab.py`（交替 A/B，见 §3.2）用「全部历史」的窗口测
`today_reports`，得出「新索引让它慢 7.5 倍」—— 差点让我删掉一个正确的索引。
实际生产传的是**一天**，用一天的窗口复测是 2.16 ms vs 2.44 ms，**持平**。
宽窗口下慢是真的（SQLite 翻转了连接顺序），但**那个窗口不存在**。

三条合起来是同一句话：**基准测试的形状，和被测系统真实运行时的形状，必须一样；
不一样的时候，测出来的东西再精确也没有意义。**

## 6. 备份与磁盘

`tools/sqlite_bench.py` 里的 `backup` 项实测：**约 990 MiB 的库，在线备份 3.75 秒**。

`backup.py` 用的是 SQLite 的 online backup API（不是 `cp`），这是对的：
事务一致，且不阻塞读者。

但要注意三件事：

1. **备份是完整副本，不是增量。** 保留规则是**按时间**（`BACKUP_KEEP_DAYS=14` 天），
   不是按份数，而且有三个数字一起决定结果：`KEEP_DAYS=14`（保留期内的一律留）、
   `KEEP_MIN=7`（至少留 7 份）、`KEEP_MAX=60`（最多 60 份，先到先算）。
   **实际份数要用模型算，不是「14 份」**——见下。
2. **库是只涨不落的**（见 §7），而备份的总占用约等于
   **份数 × 当前库大小**。库在涨，份数不变，占用就跟着涨 —— 这是最容易低估的一项。
3. **每次升级也会跑一次同样的备份**（`deploy_pilot.sh` 第 280 行），落在**同一个目录**，
   所以「一天多升级一次」就是「多一整份完整副本」。

`tools/backup_retention_model.py` 用 `prune()` 的**同一套规则**按真实日历天数模拟。
100 人每天 3 封的真实增长速度是约 **8.5 MiB/天**（7.5–9.3 KiB/封），跑满两年：

```
retention rule: keep 14 days, at least 7, at most 60
simulating 2 years from 60 MiB, growing 8.5 MiB/day

   copies/day  peak copies   peak backups    live db   total disk
          1.0           15        30.8 GiB      1.8 GiB       32.6 GiB   (只有每日定时)
          2.0           30        57.7 GiB      1.8 GiB       59.5 GiB   (每日 + 每天升级)
```

**读法**：只有每日定时任务时，稳定在 **15 份**（今天 + 往前 14 天）；但只要在这两周里
跑过升级，份数就会超过 14，因为升级备份和每日备份**抢同一份保留窗口**。
「每天升级一次」会稳定在 **30 份** —— 也就是**两周的库，乘以二**。

**备份份数是乘数，所以它是省磁盘的第一旋钮**（40 GB 盘上 `KEEP_DAYS` 14→3 让 100 人
从 26 个月变成 52 个月写满，见 `tools/disk_budget.py`）。而**压缩不是旋钮**：
负载是 AES-GCM 密文，实测 gzip 只有 1.0×。

## 7. 还没做的：保留期（这是产品决定，不是 bug）

只有 `page_views` 有保留期（180 天，`analytics.retention_days()`）。
`messages` 与 `reports` **一行都不删**。

而 `pilot_app/static/privacy.html` 是这么承诺的：

| 数据 | 承诺的保留期 |
|---|---|
| 报告正文 | 直到你删除账号 |
| 邮件元数据（发件人、主题、时间、状态） | 直到你删除账号 |
| 本校来信正文（生成失败、等待重试的） | 保留至重试成功或你删除账号 |

**代码和政策目前是一致的**，所以我**没有动它** —— 加保留期会改掉一个对用户做出的
承诺，那是产品决定，不该顺手做。

但它的后果要有数：**库随「用户数 × 每人每天的邮件数 × 时间」线性增长。**
每封信的常驻成本是「元数据 + 一份约 30 KB 的报告正文」（正文发完即清空）。

参考量级。**每封信的常驻成本是 7.5–9.3 KiB，不是本文早期版本说的 34 KiB**
（见下面的更正说明）。构成：报告信封 6.5–8.3 KiB + 邮件元数据约 1.2 KiB。

**更正（2026-09-18 晚）**：本文早先按「每封信 34 KiB」算过一版磁盘表，**偏大约 3.5 倍**，
原因有两个，都值得记下来：

1. **造数用了 `REPORT_MAX_TOKENS=4000` 的上限，不是实测**。`service.py` 自己的注释写着
   实测报告落在 **2,200–2,800 字符**，而基准测试塞的是 30 000 字节。
2. **造数塞的是重复字节，不是密文**。`b"m" * 30000` gzip 后只有 65 字节 —— 于是那个
   「990 MiB 的库」压缩到 12 MiB，基于它算出的备份占用完全是假的。
   真实负载是 AES-GCM 信封，**不可压缩**（实测 gzip 后 95%，1.0×）。
   现在 `tools/sqlite_bench.py` 的 `_payload()` 用随机字节，理由写在 docstring 里。

`tools/disk_budget.py` 用更正后的数字按真实日历天模拟（保留规则取自 `prune()`）：

| 规模（每天 3 封） | 40 GB 盘·KEEP_DAYS=14（默认） | KEEP_DAYS=7 | KEEP_DAYS=3 |
|---|---|---|---|
| **100 人** | 26 个月写满（+1.15 GiB/月） | 46 个月 | **52 个月** |
| 150 人 | 17 个月 | 31 个月 | 35 个月 |
| 200 人 | 13 个月 | 23 个月 | 26 个月 |
| 300 人 | 9 个月 | 16 个月 | 18 个月 |

（40 GB 盘按留 15% 余量算，可用 34 GiB，另计 4 GiB 系统与程序开销。）

**读法**：备份份数是**乘数**（默认 15 份，所以备份约是线上库的 15 倍）。
库本身涨得慢（100 人每天 3 封 ≈ 2.6 GiB/年），**所以省磁盘的第一旋钮是份数**：
`KEEP_DAYS` 从 14 降到 3，100 人从「两年出头写满」变成「四年多」。

```bash
# 40 GB 盘上的推荐配置
echo "INFE_PILOT_BACKUP_KEEP_DAYS=3" | sudo tee -a /etc/cityu-mail-pilot/pilot.env
```

**注意这一次不能顺手调小 `INFE_PILOT_REPORT_MAX_TOKENS`**：报告格式是固定的七个小节
（`prompts.py`），把上限压到实测长度以下会**截断报告**，不是「精简报告」。
真要缩小报告，正确的路是改用简报模式（`INFE_PILOT_BRIEF_FIRST=1` /
`INFE_PILOT_FULL_REPORT=0`，简报上限本就是 1200 token），那是产品决定，不是磁盘优化。

**如果哪天真不够用**：唯一的长期手段是给 `reports` 加保留期 —— 但**必须先改隐私政策**
（它承诺「报告正文保留到你删除账号」），顺序不能反。

完整实测见 `docs/sqlite-performance-2026-09-18.md` §6。

如果哪天决定改保留期，正确的顺序是：**先改隐私政策、再改代码、最后跑迁移**，
而不是反过来。

## 8. 真要往 200 人以上走，该做什么

按性价比排序：

1. **先量再改。** 现在有脚本了：`sqlite_index_audit.py`、`sqlite_profile_calls.py`、
   `http_loadtest.py`、`sqlite_loadtest_sweep.py`。任何「我觉得这里慢」都应该先被
   其中一个量一遍。
2. **多进程（已经验证过，是扩容的第一步）。** 实测同一个库文件上 3 个 web 进程
   = **2.8 倍吞吐、延迟 1/3、零锁错误**（§4.2）。nginx 已经在前端，按 upstream
   分发即可；`MemoryMax`/`TasksMax` 要跟着进程数放大。
3. **一条请求少开几个连接。** 现在 `/api/me` 要开 10 个连接、每个请求共约 15 个，
   而每次连接的固定成本约 0.8 ms —— 也就是说**仪表盘那 40 ms 里约 10 ms 是纯连接
   开销**（§3.4）。把同一请求的读合并到一次连接（或按线程复用连接）能直接省掉它。
   **代价是 `connect()` 的语义要改，250 多个调用点都要逐个看**（还有
   `_relax_message_status_check` 里自己 `BEGIN` 的那段），所以要单独一轮、带自己的
   测试。**单进程上限是 Python 侧串行化，这是最直接削掉它的办法。**
4. **减少每请求的写入/fync。** 每个请求都要 `touch_last_seen` + 一次访问记录插入，
   而 `synchronous` 目前是 `FULL`。WAL 下 `NORMAL` 是常用且基本安全的设置
   （掉电可能丢最后几条事务，但库不会损坏），也是 `tools/sqlite_settings_probe.py`
   里 **C 变体写入 p50 1.027 ms vs B 1.610 ms** 的那个差别。
   **这一轮没有改它**：这是拿持久性换吞吐的取舍，要单独决定，不该夹在性能改动里。
5. **保留期**（§7）—— 纯粹为了磁盘，先改政策。
6. **只有到这一步才考虑换数据库**（PostgreSQL）。而换的理由会是「多机写入」，
   不是「SQLite 慢」—— 实测说明它不慢，多进程也验证过了。

## 9. 怎么复核这一轮的结论

```bash
# 1. 每次改动后先跑这个（8 项，秒级）
python tools/smoke_check.py

# 2. 造一份 100 人的库并量全部指标（约 1 分钟）
python tools/sqlite_bench.py --users 100 --messages-per-user 300 \
    --reports-per-user 300 --page-views 200000 --json docs/_bench.json

# 3. 逐调用定位（哪个调用慢，一行一行看）
python tools/sqlite_profile_calls.py --users 100 --messages-per-user 300 \
    --reports-per-user 300 --page-views 200000 --rounds 30

# 4. 索引审计（删掉每个索引再量一次；新增索引必须先过这一关）
python tools/sqlite_index_audit.py <库文件> --users 20 --rounds 25

# 4b. 交替 A/B：同一份库上反复删/建索引，看整个调用集合（含执行计划翻转）
python tools/sqlite_index_ab.py --users 100 --cycles 3 --rounds 12

# 4c. 备份到底占多少磁盘（保留规则 + 库增长）
python tools/backup_retention_model.py --years 2 --start-mb 60 --mb-per-day 10

# 4d. 给定磁盘大小，能撑多久 / 能装多少人
python tools/disk_budget.py --disk-gb 40 --users 100 --mails-per-user-day 3

# 5. 并发曲线（真实的「多少人会卡」）
python tools/sqlite_loadtest_sweep.py <库文件> --rates 0.25,1,2,5,10 --seconds 15

# 5b. 端到端 HTTP：真人节奏（--think 2）与上限（--think 0），以及多进程验证
python tools/http_loadtest.py <库文件> --clients 16 --seconds 20 --think 2
python tools/http_loadtest.py <库文件> --clients 32 --seconds 15 --servers 3

# 6. 生产尺寸的迁移演练（幂等、不丢行、多久）
python tools/sqlite_migration_check.py <库文件>

# 7. 连接设置的对照实验（只改一个变量，随机顺序，多次取中位数）
python tools/sqlite_settings_probe.py --users 100 --repetitions 3
```

**本文引用的中间产物 JSON 已全部删除**（原先留在 `docs/` 下的 6 个 `_*.json`）。
参数都在上面，重跑比读一份可能过期的快照可靠；而 `docs/` 里只有白名单文档会被发布，
留那些 JSON 只是本地垃圾。

**三个一次性脚本也已删除**，它们的答案已经写进本文，留着只会让人去重跑一个已经有答案的
问题而不是读结论：

| 删掉的脚本 | 它回答了什么 | 答案在 |
|---|---|---|
| `sqlite_query_candidates.py` | `today_reports` 改成按 `reports.created_at` 排序值不值得 | 快 1.42 倍，但**改变了「按收信时间排」的语义**，未采纳（§5） |
| `sqlite_queue_plan.py` | 为 worker 的 `ORDER BY created_at` 加索引有没有用 | 没有：SQLite 从不选它，删掉后只差 −0.61 ms（`database.py` 的 `RETIRED_INDEXES`） |
| `sqlite_received_index_check.py` | `idx_messages_received` 在不同窗口下是帮忙还是添乱 | 按**生产的一天窗口**是持平/略好，按宽窗口会翻转执行计划变慢；索引保留（§5） |

**升级到这一版时要注意**：`initialize()` 会在启动时 ① 建 2 个索引 ② 删 3 个
上一版建过的索引。约 990 MiB 的库上实测 0.0 秒（索引已存在），但**一个从未跑过新版
索引的库会在这里花几十秒**（建两个索引要扫表）—— 属于正常，不要在部署脚本里
把它当成卡死。部署脚本本来就会先备份数据库，这次备份正好用得上。

## 10. 还没有解决的一件事：运营者面板的一条查询仍然慢

`/api/admin/users` 在**约 990 MiB 的库上实测 p50 2.4 秒**（1 个运营者；
8 个并发时 5.6 秒）。比改之前的 46 秒好了 20 倍，但仍然是「点一下等两秒」。

原因不是索引，是**形状**：`list_users_overview` 对每个账号跑 7 个相关子查询
（邮件数、已分析数、队列深度、报告数、最后报告时间、已发送时间、失败数），
100 个账号就是 700 次索引查找。索引让每一次都变快，但次数没变。

**它还不影响上线**：面板是运营者一个人用的，2.4 秒可以忍受；而且这个数字来自一个
**200 000 条访问记录 + 30 000 封信**的库，真实试点远小于此。
要修的话方向是**把它折成一条 `GROUP BY`**（一次扫描算出每账号的几个计数），
而不是继续加索引。这属于单独一轮的工作，本轮没有做，因为**要动查询语义**，
而它已经不在关键路径上。
